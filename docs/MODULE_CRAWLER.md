# 关键模块：采集子系统

> 相关：[README.md](./README.md)（项目速览）、[DATA_MODEL.md](./DATA_MODEL.md) §5、[OPEN_QUESTIONS.md](./OPEN_QUESTIONS.md)

**这是本项目技术复杂度最高的模块**，也是唯一有外部依赖、唯一会"自己坏掉"的模块。
其余模块（登录、组队、日历）都是常规 CRUD，写一次就稳了；采集要长期跟网站改版搏斗。

---

## 1. 模块定位

**做**：自动发现新竞赛、自动更新报名与赛程时间。
**不做**：判断级别、推免加分、赛制 —— **官网通知里不会写"这是国家级"**，判断类字段必须人工。

| 爬虫能自动搞定 | 仍需人工补全 |
|---|---|
| 发现新竞赛、竞赛名称、来源链接 | **级别（四档）、推免加分** |
| 报名开始/截止、比赛时间 | 赛制（个人/团队人数） |
| 主办方、通知原文 | 难度评分、经验帖、获奖记录 |

## 2. 流水线

```
CrawlSource (配置：URL + 频率 + 选择器)
      │
      │ ① 调度：@nestjs/schedule 按源 cron 触发
      │    加 Redis 锁，防止上一轮没跑完就重入
      ▼
② Fetcher ── undici，超时 10s，重试 2 次，串行、间隔 ≥3s
      │        正确处理 GBK / UTF-8 编码（见 §4.1）
      ▼
   原始 HTML ──► contentHash 存 CrawlSnapshot
      │
      │ ③ Differ：hash 未变 → 直接结束（省掉 90% 的无用解析）
      ▼
④ Parser ── 按源的 CSS 选择器 / JSON API 抽取 → 结构化候选条目
      │        ⚠️ 中文日期抽取是最大难点，见 §4.2
      ▼
⑤ Matcher ── 标题相似度匹配已有竞赛
      │        ├─ 命中 → 生成"更新"动作
      │        └─ 未命中 → 生成"新建草稿"
      ▼
⑥ Guard（异常拦截器）── 命中任一规则 → 不发布，写 CrawlAnomaly + 告警
      │
      ▼
⑦ Publisher ── 事务写入 Competition / CompetitionTimeline
               ├─ 同时写 CrawlRevision（含旧值，供回滚）
               └─ isLocked 的节点跳过（见 §6）
      │
      ▼
⑧ 熔断检查 ── 本轮更新数 > 20 或连续 3 次触发拦截 → 暂停该源 + 告警

                    用户纠错 / 管理员回滚 ← 事后纠错通道
```

## 3. 调度与并发

```ts
// 每个源一个独立 cron，频率存在 CrawlSource.cron
@Cron(CrawlSource.cron)
async runSource(sourceId: string) {
  // ⭐ 必须加锁：某源跑 5 分钟，5 分钟后又触发一次，会重复写入
  const lock = await redis.set(`crawl:lock:${sourceId}`, '1', 'EX', 600, 'NX');
  if (!lock) return;                       // 上一轮还在跑，跳过

  try { await this.pipeline(sourceId); }
  finally { await redis.del(`crawl:lock:${sourceId}`); }
}
```

**串行、不并发**：源之间排队执行，不是一个源内部并发。
理由：2C2G 机器上并发抓取只会让内存尖峰叠加，而采集根本不需要快 —— 每天跑一次，跑 20 分钟和跑 2 分钟没有区别。

## 4. 三个最容易翻车的地方

### 4.1 编码：国内高校网站的 GBK 陷阱 ⭐

**大量国内高校/政府网站的 HTML 是 GBK 编码的。** 用 `fetch().text()` 直接读会得到一片乱码，然后你的日期正则全部匹配失败 —— 而且**不报错**，只是静默抓不到东西。

```ts
const buf = Buffer.from(await res.arrayBuffer());

// 优先级：HTTP header charset > <meta charset> > 默认 utf-8
const charset =
  parseCharset(res.headers['content-type']) ??
  parseMetaCharset(buf.toString('latin1').slice(0, 2048)) ??   // meta 在前 2KB
  'utf-8';

const html = iconv.decode(buf, charset);   // 依赖 iconv-lite
```

**这条务必先写。** 它是"静默失效"最常见的成因之一。

### 4.2 中文日期抽取 ⭐⭐ 最大难点

通知正文里的时间是这样的：

| 原文 | 难点 |
|---|---|
| `2026年10月15日 17:00` | 尚可 |
| `即日起至10月15日` | **缺年份**，需结合发布时间推断 |
| `2026-10-15` / `2026/10/15` / `10.15` | 格式多样 |
| `报名截止时间：10月15日（周三）17:00` | 混入星期 |
| `详见附件` | **根本没有时间** |
| `初赛：10月下旬` | **只有模糊区间** |

**建议策略**：
1. 先写一个针对中文的日期正则库，覆盖上述常见格式
2. **缺年份时用通知的发布时间补全**，并额外判断"是否已过"—— 若算出来的日期早于发布时间，说明是明年
3. 模糊表达（"10月下旬"）**不要猜**，抽不出来就不写，留给人工
4. **抽不出来是最常见且正常的结果**，程序必须优雅处理（不写入、不报错），而不是崩溃或写脏数据

**这一块的单元测试要写厚。** 它是最容易产生"日期变成 1970 年"的地方，而异常拦截器只是最后一道防线。

### 4.3 匹配：不要把同一个竞赛建两遍

```ts
// 标题相似度，按优先级
1. 精确匹配 aliases（别名表）
2. pg_trgm:  SELECT id, similarity(name, $1) AS s FROM "Competition"
              WHERE name % $1 ORDER BY s DESC LIMIT 5
3. 阈值：
   s > 0.6  → 自动判定为同一竞赛，走"更新"
   0.3 ~ 0.6 → 标记"疑似"，进人工确认（这条不阻塞发布，只提示）
   s < 0.3  → 新建草稿
```

**同类归一化**：先剥离年份、去掉"第X届""关于举办""的通知"等噪声词再比对，否则 "2026年电子设计竞赛" 和 "2025年电子设计竞赛" 会被判成两个竞赛。

## 5. 异常拦截器（安全带 ①）

**这是投入产出比最高的一段代码**，用几条规则就能挡住最丢人的事故。

```ts
const RULES = [
  // 日期合理性
  { name: 'date-out-of-range', check: d => d.getFullYear() < 2020 || d.getFullYear() > 2035 },
  { name: 'epoch-date',        check: d => d.getFullYear() === 1970 },

  // 逻辑矛盾
  { name: 'end-before-start',  check: (start, end) => end < start },

  // 跳变过大
  { name: 'jump-too-large',    check: (oldV, newV) => daysBetween(oldV, newV) > 180 },

  // 空值覆盖
  { name: 'null-overwrite',    check: (oldV, newV) => oldV != null && newV == null },
];
```

命中任一 → **不发布，保留原值，写 `CrawlAnomaly` + 告警**。

**必须注意**：拦截器是**最后一道防线，不是第一道**。它拦不住"日期格式对了但抽错了字段"这类错误 —— 那要靠 §4.2 的测试和用户纠错。

## 6. ⭐ 人工锁定机制

**问题**：管理员手工修正过一个被解析错的截止时间后，下一次采集会把它**改回去** —— 而且看起来像"数据自己变回去了"这种灵异现象。

**方案**：`CompetitionTimeline.isLocked`

```
人工编辑某个节点 → isLocked = true
                        ↓
采集遇到 isLocked = true 的节点 → 不写入，只记录冲突告警
                        ↓
管理员可在后台看到"源 X 想把这个值改成 Y，但该值已被人工锁定"
```

> 这个机制不在原设计稿里，是拆分文档时补的。**没有它，人工修正形同虚设。** 见 [OPEN_QUESTIONS Q9](./OPEN_QUESTIONS.md)。

## 7. 熔断与告警（安全带 ④⑤）

| 触发条件 | 动作 |
|---|---|
| 单源连续失败 3 次 | `health = FAILING` + 告警 |
| 单源连续 N 天抓取条目数 = 0 | `health = DEGRADED`，**选择器很可能已失效** + 告警 |
| 单源单轮更新数 > 20 条 | **熔断：暂停该源** + 告警 |
| 单源连续 3 次触发异常拦截 | **熔断：暂停该源** + 告警 |

> **"连续 N 天抓取数为 0"是最重要的一条告警。** 网站改版后，爬虫不报错、只是再也抓不到东西，数据悄悄烂掉。全自动发布模式下没人看队列，只能靠这条告警发现。

## 8. 合规红线

- 严格遵守 `robots.txt`，**解析并尊重其中的 Crawl-delay**
- 单源抓取间隔 ≥ 3 秒，串行抓取
- **只存结构化字段 + 原文链接，不转载全文**（`CrawlItem.rawText` 仅用于解析，不对外展示）
- 只抓公开页面，不绕过登录/验证码
- 用户可见处标注「信息来源：XX 官网 ↗」

---

## 9. 选源标准（给运维者的判断依据）

**✅ 好抓的源**
- 服务端渲染的 HTML 列表页（教务处、学院官网通知栏）
- 结构稳定的 CMS 输出（列表页固定 `ul > li > a > 标题 + 日期`）
- 有公开 JSON API 的站点

**❌ 难抓 / 别碰的源**
- 纯前端 JS 渲染（打开是 `<div id="app"></div>`）→ **要么找到它背后的 JSON API，要么放弃改人工录入**
- 需要登录的
- 结构频繁变动的
- 附件是 PDF 的（**没有 PDF 解析能力，别承诺**）

> **判断方法**：浏览器打开目标页 → 右键"查看网页源代码"（不是"检查"）→ 如果能看到竞赛标题，说明是服务端渲染，好抓；如果源代码里没有标题、只有一堆 `<script>`，就是 JS 渲染，放弃。

## 10. 实施顺序（重要）

```
第 1 步：Fetcher + 编码处理 + 单源跑通（先能拿到正确的 HTML）
第 2 步：Parser + 中文日期抽取 + 单元测试
第 3 步：Publisher + CrawlRevision 版本记录
第 4 步：异常拦截器   ← ⭐ 必须在接第 3 个源之前完成
第 5 步：Matcher + 去重
第 6 步：熔断与告警
第 7 步：多源扩展
```

**纪律：先有刹车，再踩油门。**
前 1–2 个源数据量小、你能盯着看；源一多就盯不住了。**异常拦截器完成之前，不要接入第 3 个源。**
