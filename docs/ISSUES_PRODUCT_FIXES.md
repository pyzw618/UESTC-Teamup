## Issue 1｜组队帖增设"组队意愿"相关内容

### 现状 / 问题

广告牌模式下，QQ / 微信直接完整公开在帖子详情上，看帖 → 拿到联系方式之间没有任何动作与痕迹：
- 招募人完全不知道有哪些人看过、对帖子感兴趣，只能干等；
- 意向人数这一最有价值的信号没有被展示和利用。

### 修改方向

1. **联系方式加门槛**：帖子详情页的联系方式默认遮挡；用户点击「我想组队」类按钮后才可见。点击行为即登记一条"组队意愿"。
2. **意愿计数对外展示**：帖子列表项与详情页外层显示「有 X 人有组队意愿」。同一用户对同一帖子只计一次（数据库层唯一约束兜底），支持再次操作撤销意愿。
3. **招募人站内消息**：招募人（发帖人）登录网站时收到站内消息，告知**哪个帖子**有多少人有组队意愿；消息中心有红点。同一帖子的多条意愿做聚合展示（追加或更新计数），避免刷屏。
4. **数据模型**：新增组队意愿记录（帖子 id + 用户 id + 时间），`(teamId, userId)` 唯一；意愿人数由计数查询或冗余计数字段得出。

### 待定项

- 游客（未登录）能否点击按钮？建议：不可，点击时引导登录（与"注册用户可见联系方式"的现有边界一致）。
- 是否同时向游客展示「有 X 人有组队意愿」？建议：展示计数、不展示任何人身份信息。

### 验收标准

- 不点击按钮看不到联系方式；点击后可见且计一次意愿，重复点击不重复计数，可撤销。
- 帖子外层能看到「有 X 人有组队意愿」，数字随行为实时正确。
- 发帖人登录后能在消息中心看到"某帖有 X 人有组队意愿"的消息。

## Issue 2｜CONTRIBUTOR 角色开放竞赛编辑权限 + 支持竞赛自定义字段

### 现状 / 问题

- CONTRIBUTOR（贡献者）角色已存在于角色枚举、后台用户管理可设置，但**所有竞赛编辑接口仅 ADMIN 可调**，贡献者实际上没有任何权限——为"科协共建"预留的角色有名无实。
- 竞赛字段固定（名称、主办方、级别、时间线、加分、标签等），无法表达各竞赛特有的信息（如数模竞赛的"QQ 交流群号"、电赛的"器材清单"）。

### 修改方向

1. **权限放宽**：CONTRIBUTOR 可编辑竞赛信息（复用现有编辑接口，守卫从 `@Admin()` 放宽为 ADMIN / CONTRIBUTOR）。所有编辑照常进入版本留痕（`CrawlRevision`，origin=MANUAL），可回滚；管理员可锁定字段、撤销贡献者的修改。普通用户权限不变。
2. **自定义字段（新增表项）**：支持有编辑权限的用户为**单个竞赛**新增自定义键值属性。
   - 数据模型建议：竞赛下挂自定义字段键值对（独立键值表或 JSON 字段均可，键值表更利于按 key 检索与留痕）。
   - 键名约束：长度上限、合法字符集；值为纯文本，展示时转义，防 XSS。
   - 前台在竞赛详情页新增「补充信息」区块展示自定义字段；后台编辑页可增删改。
   - 自定义字段的修改同样进入版本留痕。

### 待定项

- 自定义字段是否允许"提升"为全局模板字段（同一类竞赛共用）？本期先不做，留到有真实使用数据后评估。
- CONTRIBUTOR 名单的授予节奏（哪些科协、谁负责授）由运营侧确认。

### 验收标准

- 管理员把某用户设为 CONTRIBUTOR 后，该用户能修改竞赛信息、能为竞赛新增自定义字段并展示在详情页；修改留痕、可回滚。
- 普通用户仍无法编辑竞赛信息。

## Issue 3｜删除所有限流

### 现状（限流点盘点，供逐项移除）

| 位置 | 内容 |
|---|---|
| `auth.service.ts` | 验证码：60s 重发冷却、同邮箱每日 5 次、同 IP 每日 20 次、全局每分钟 10 次、验证码错 5 次作废 |
| `auth.service.ts` | 密码登录：连续失败 5 次锁定 15 分钟 |
| `users.controller.ts` | 公开名片页：每 viewer/IP 每分钟 60 次 |
| `comments.service.ts` | 评论发布：每分钟 10 条 |
| `teams.service.ts` | 发帖：活跃帖上限 5 条、同竞赛 24h 去重、发帖 Redis 锁 |

### 修改方向

移除上述接口级 / 业务级限流逻辑。注意：cron 任务的 Redis 防重入锁（jobs）**不属于限流，保留**；多实例防重入同理保留。

### ⚠️ 风险提示（执行前需评审确认）

现有这些限流同时承担着：密码爆破防护（登录失败锁定）、验证码邮件成本与轰炸防护（发码配额）、联系方式与学号等个人信息防批量爬取（名片页限流）。全部移除后，公开接口可被脚本无成本批量抓取、账号可被无限爆破。**建议**：移除限流的同时，至少为"密码登录失败锁定"与"验证码发送配额"保留替代防护（如图形验证码 / 人机验证），或在发码、名片页等敏感入口上单独确认豁免。此项建议在实施前单独过一次评审。

## Issue 4｜公开可见性收敛：只有"招募中"的帖子对外展示

### 现状 / 问题

公共发现列表允许勾选展示「已满员 / 已参赛」（`DISCOVERABLE_STATUSES` 含 FULL / COMPETING）；非招募状态帖子通过直链也能被任何人访问。"已满员 / 已参赛"的帖子挂在公共列表里属于噪音，也削弱"招募中"的密度感。

### 修改方向

1. 公开列表、搜索、竞赛详情页"正在招募的队伍"区块**只返回 RECRUITING** 的帖子，不再提供勾选展示其他状态。
2. 非 RECRUITING 状态（FULL / COMPETING / DISBANDED）的帖子：**仅发布者本人（及管理员）可访问**，他人访问返回 404 / 不存在提示（不暴露帖子存在性）。
3. 发布者在「我的帖子」中可见并管理自己全部状态的帖子（含已解散的归档仓库，维持现状）。
4. 服务端实施权限，不依赖前端隐藏。

### 验收标准

- 游客与其他用户无论从列表、搜索还是直链，都看不到非"招募中"的帖子。
- 发布者登录后能在「我的帖子」看到并管理自己所有帖子。

## Issue 5｜增设反馈渠道（双入口）+ 后台单日 JSON 导出

### 现状 / 问题

- 功能性问题没有反馈入口；竞赛信息有误只能走"字段纠错"，缺少自由文本的整体反馈通道。
- 后台没有面向运营的反馈导出能力。

### 修改方向

**1. 两个反馈入口**

| 入口 | 位置 | 类型 | 自动附带 |
|---|---|---|---|
| 功能问题反馈 | 全站状态栏（导航栏） | `FUNCTION` | 当前页面路径（便于定位） |
| 竞赛信息问题反馈 | 各竞赛详情页 | `COMPETITION_INFO` | **竞赛名**（competitionId + 提交时名称快照，防竞赛改名后对不上） |

反馈内容为自由文本；可附选填的回访联系方式。数据模型：`Feedback(id, type, competitionId?, competitionName?, pagePath?, content, contact?, userId?, createdAt)`。

**2. 后台导出**

- 新增后台反馈管理页，提供「导出反馈」按钮。
- 反馈可**按日期选择**，一次只能下载**一天之内**的反馈；如该日期当天没有反馈，日期置灰、不可下载。
- 点击按钮即下载该日全部反馈的 JSON 文件。

**3. 导出 JSON 格式设计**

```json
{
  "meta": {
    "exportedAt": "2026-09-27T20:15:30+08:00",
    "date": "2026-09-27",
    "total": 2
  },
  "items": [
    {
      "id": "cmdxxxx",
      "type": "FUNCTION",
      "pagePath": "/competitions/abc123",
      "competition": null,
      "content": "日历页在手机上月份切换按钮点不到",
      "contact": "",
      "submittedBy": { "userId": "cmu1234", "nickname": "银杏" },
      "createdAt": "2026-09-27T14:03:21+08:00"
    },
    {
      "id": "cmdyyyy",
      "type": "COMPETITION_INFO",
      "pagePath": "/competitions/abc123",
      "competition": { "id": "abc123", "name": "全国大学生数学建模竞赛" },
      "content": "报名截止时间与官网不一致，官网显示 10 月 20 日",
      "contact": "QQ 123456",
      "submittedBy": null,
      "createdAt": "2026-09-27T09:41:07+08:00"
    }
  ]
}
```

格式要点：`meta` 记录导出时间、所选日期与条数；`items` 每条含类型、可选的竞赛对象（含提交时名称快照）、内容、选填联系方式与提交者；游客提交时 `submittedBy` 为 `null`。字段均为 snake 兼容、可被脚本直接消费。

### 待定项

- 游客能否提交反馈？建议：允许（附选填联系方式），否则会漏掉未注册用户的意见；若担心滥用，可要求登录。
- 反馈是否需要后台"已处理"状态流转？本期仅导出即可，状态流转留待下期。

### 验收标准

- 状态栏入口可提交功能反馈；竞赛详情页入口提交时自动注明竞赛名。
- 后台选择日期可下载该日反馈 JSON；无反馈的日期置灰不可下载；JSON 符合上述格式。

## Issue 6｜竞赛增加 `year` 届次字段

### 现状 / 问题

竞赛档案没有届次概念，同一赛事（如数模国赛）各年份的时间线、通知、组队帖都挂在同一实体下，运行跨年后数据互相覆盖、混杂，历史数据无法单独查看。

### 修改方向

1. `Competition` 增加 `year`（届次年份，整数，必填）。
2. 唯一索引从「名称唯一」调整为「名称 + 年份唯一」，同一赛事可存在多个年份的档案且互不覆盖。
3. 竞赛列表 / 日历 / 搜索默认只展示**当前年份**（或最新届），提供年份切换查看历史届次；组队帖、关注、提醒随所在届次走。
4. 后台编辑表单、种子数据同步补充年份字段；存量数据按现有时间线年份回填。

### 验收标准

- 同一竞赛能存在两个年份的档案，互不覆盖、互不干扰。
- 列表 / 日历默认只显示当年，切到历史年份能看到旧档案。
